# AI Document Checker — план развития после M16

**Дата:** 4 октября 2026 года

**Статус:** M17–M21 выполнены
**Основа:** аудит проекта и приёмочные проверки, выполненные 3–4 октября 2026 года; результаты M17–M21 внесены ниже.

## 1. Связь с действующими планами

Основные milestones M01–M16 отмечены завершёнными в [`DEVELOPMENT_PLAN.md`](../DEVELOPMENT_PLAN.md). Этапы APP-M01–APP-M03 по помощи в интерфейсе отмечены завершёнными в [`APP_ASSISTANT_PLAN.md`](APP_ASSISTANT_PLAN.md). Этот документ продолжает основной план с M17 и не переоткрывает уже принятые этапы.

Базовый аудит подтвердил сквозные E2E-сценарии для всех 13 заявленных расширений. В ходе M17 предоставленная пользователем XLSX-книга была проверена локально: MIME и OOXML-структура корректны, native-парсер и MarkItDown завершаются успешно, а upload-маршрут принимает книгу и сохраняет исходные байты. В книге 122 строки данных и нет формул, поэтому формульную ошибку на ней воспроизвести нельзя; исходная браузерная ошибка в текущем окружении не повторилась. Проверка выявила отдельную проблему нормализации: MarkItDown выдавал `NaN` для пустых XLSX-ячеек, теперь карта Markdown восстанавливает пустые значения по native-источникам. На исходном baseline голосовой ввод был заглушкой; реализация и результаты M18 приведены ниже. M20 вынес PDF renderer и worker в загрузку по требованию и добавил проверку gzip-бюджета стартового JS.

## 2. Общие правила выполнения

- Выполнять milestones последовательно: M17 → M18 → M19 → M20 → M21. Не включать работу следующего этапа в текущий без отдельного решения.
- Сначала сверять код, Git, проектные инструкции и актуальные тесты. Не дублировать уже работающий функционал.
- Сохранять неизменность оригинала, версий анализа, истории чатов и маршрутизации citation.
- Не вычислять формулы Excel, не выполнять макросы, пользовательский HTML/JavaScript, EPUB-скрипты или другие активные данные.
- Не передавать аудиозапись, полный документ, весь Markdown, индекс или невыбранные документы во внешнюю модель без отдельного информированного согласия.
- Передавать в AI только минимальный контекст, необходимый для конкретного запроса; сохранять текущую изоляцию по чату и выбранным документам.
- Для каждого milestone сначала зафиксировать сценарии приёмки, затем выполнить изменения, тесты, документацию и проверить итоговый diff.
- Отделять проверки с подставным провайдером от opt-in проверки реальной авторизации Codex.
- После закрытия этапа обновить этот файл и `TESTING_REPORT.md` фактическим статусом, командами и результатами.

## 3. Milestones

## M17. Надёжность XLSX и точность формул

**Статус:** выполнен 3 октября 2026 года. Итоги и проверенные ограничения зафиксированы в [`TESTING_REPORT.md`](../TESTING_REPORT.md).

### Цель

Установить причину наблюдавшейся пользователем ошибки загрузки Excel-книги либо доказать, что проблема зависит от конкретного файла; сделать представление формул и их сохранённых результатов понятным анализу, оригиналу и пользователю. Для обычных XLSX/XLS сохранить текущую успешную загрузку и просмотр.

### Основные задачи

1. Проследить путь XLSX по коду от `<input accept>` и HTTP upload до проверки MIME/сигнатуры, сохранения, worker, native parser, MarkItDown, индексации, table preview и citation. Основные области: `frontend/src/App.tsx`, `backend/app/api.py`, `backend/app/services/document_security.py`, `backend/app/services/parsing.py`, `backend/app/services/document_worker.py`, `backend/app/services/table_analysis.py` и `frontend/src/components/OriginalDocumentViewer.tsx`.
2. Если пользователь предоставит файл, воспроизвести отказ локально и записать безопасную диагностику: фактическое расширение, MIME, сигнатура, этап отказа и отображаемая ошибка. Не добавлять потенциально личную книгу в репозиторий и не выводить её ячейки, имя листа или имя файла в публичные логи.
3. Если файл не предоставлен, создать синтетические regression-fixtures, охватывающие структурно возможные причины отказа. Отметить дефект конкретной книги как непроверенный до воспроизводимого примера.
4. В `parsing.py` отдельно сохранять для XLSX значение ячейки и формулу, если формула существует; не запускать вычислитель формул. Сохранить sheet/row/column/cell locators в источниках и Markdown-карте.
5. Согласовать извлечение с `table_analysis.py`: отличать обычное значение, формулу с сохранённым результатом и формулу без такого результата. Не подменять отсутствующее значение нулём или пустой строкой без явного статуса.
6. В оригинальном viewer и контексте анализа явно обозначать формулы, для которых нет сохранённого результата. Сохранить безопасную пагинацию, выбор листа, фильтрацию и переход citation к правильной ячейке/строке.
7. Ошибки «неверный формат», «повреждён», «зашифрован», «превышены лимиты» и «не удалось преобразовать» должны оставаться различимыми; сбой MarkItDown не должен уничтожать успешный native fallback.
8. Обновить README/API-контракт при изменении видимого поведения формул или классификации XLSX-ошибок.

### Зависимости

- Текущая версия парсера и таблиц из `backend/app/services/parsing.py` и `table_analysis.py`.
- Пользовательская книга нужна только для точного воспроизведения его конкретного отказа; общая работа и синтетические regression-тесты от неё не зависят.

### Проверки

- Unit: XLSX с постоянными значениями; формула с cached value; формула без cached value; несколько листов; пустые строки/ячейки; строковые и числовые форматы; некорректная структура; MIME/signature mismatch; превышение лимита; шифрование.
- Integration: успешный upload сохраняет исходные байты; worker завершает обработку; ошибка конвертера не оставляет частичный активный индекс; retry не теряет оригинал, чат и успешную прошлую версию.
- E2E: исходный workbook → таблица → лист/строка по citation → Markdown → скачивание → reload.
- Проверить на синтетической книге, что формулы не вычисляются и пропуск cached value явно показан.

### Критерии готовности

- Обычная XLSX-книга и многолистовая книга проходят полный текущий поток без регрессии.
- Для воспроизводимого пользовательского файла исправлена подтверждённая причина; если файл не предоставлен или ограничение формата намеренное, это указано явно, а ошибка остаётся понятной.
- В ответах не выдаётся формула без cached value за вычисленный результат.
- Оригинальные байты не меняются; citation однозначно указывает книгу, лист и исходную область.
- Все новые regression-тесты и целевые существующие parser/table/preview/API/E2E-тесты проходят.

## M18. Приватный голосовой ввод в composer

**Статус:** выполнен 3 октября 2026 года. Реализация и результаты проверок зафиксированы в [`TESTING_REPORT.md`](../TESTING_REPORT.md).

### Цель

Заменить заглушку микрофона на управляемую диктовку: распознанный текст добавляется в поле сообщения и остаётся на проверку пользователя. Голос не отправляется автоматически вместе с аудио или сообщением.

### Основные задачи

1. Удалить заглушечный `onVoiceInput` в обоих composer-потоках `frontend/src/App.tsx` и реализовать состояния в `frontend/src/components/AIComposer.tsx` либо в изолированном hook/service.
2. Запрашивать доступ к микрофону только после явного нажатия. Реализовать состояния: готово, запрос разрешения, запись, распознавание, текст добавлен, остановлено, запрещено, устройство отсутствует, язык недоступен, ошибка и неподдерживаемый браузер.
3. Использовать локальное распознавание только когда браузер явно подтверждает поддержку on-device режима (`SpeechRecognition.processLocally` и доступный языковой пакет). Никогда не переключаться автоматически на браузерную/сетевую обработку.
4. Если совместимый пакет для диктовки доступен для загрузки, показать отдельное действие установки через `SpeechRecognition.install`; сообщить, что оно загружает пакет и не включает микрофон. После успеха пользователь отдельно запускает диктовку.
5. Если локальная диктовка для языка/качества недоступна либо локальный API не поддерживается, оставить composer рабочим и предложить печатать или открыть отдельный browser-managed fallback.
6. Перед browser-managed распознаванием показать доступный диалог согласия: браузер может передать звук внешнему сервису; приложение не знает поставщика и сроков хранения; согласие действует только на эту диктовку и не сохраняется. Без явного продолжения обработчик не запускается.
7. Распознанный текст вставлять в текущий draft в предсказуемую позицию, не стирать уже введённый текст. Пользователь может отредактировать, удалить или повторно записать текст.
8. Запись останавливается явной кнопкой, при отмене, закрытии/размонтировании composer и при уходе со страницы. Ошибка разрешения не должна оставлять UI в состоянии «запись».
9. Клавиатурная активация, видимый focus, корректные `aria-label`, `aria-pressed`/`aria-live`, доступный статус без перехвата фокуса; reduced-motion не должен скрывать состояние записи.
10. По умолчанию аудио не загружается в backend, не сохраняется на диск и не передаётся внешнему сервису приложением. Browser-managed fallback может использовать внешний сервис только после отдельного согласия; обычный распознанный текст попадёт в AI только после явной отправки через composer.

**Дополнение — визуальный уровень сигнала:** после явного запуска диктовки допустим отдельный `getUserMedia({ audio: true, video: false })` для локального `AnalyserNode`. Поток не записывается и не отправляется; его дорожки останавливаются при остановке, отмене, ошибке, скрытии страницы и размонтировании. Ошибка необязательного измерителя не блокирует распознавание и показывает статичный индикатор вместо фиктивной шкалы.

### Зависимости

- Существующий `AIComposer`, обработка отправки/отмены сообщения и дизайн-система.
- Перед выбором browser API проверить поддержку в целевых браузерах; документация MDN отмечает ограниченную доступность и отдельные правила локального распознавания.

### Проверки

- Unit/component с имитацией API распознавания: начало/остановка, добавление текста к draft, отмена, denied permission, отсутствие устройства, пустой transcript, ошибочный язык и завершение при размонтировании.
- Проверка, что отправка вызывается только кнопкой отправки/Enter после изменения текста и никогда автоматически по завершению записи.
- Browser E2E desktop и mobile: доступность кнопок, фокус, live-status, сохранение несвязанного draft и отсутствие horizontal overflow.
- Тест отсутствия audio upload/request и отсутствия аудио-файлов в API, volumes и diagnostics.
- Отдельный ручной smoke в браузере с реальным разрешением микрофона, если окружение тестирования это допускает; моковый тест не называть проверкой распознавания реальной речи.

### Критерии готовности

- В поддерживаемом локальном режиме речь превращается в редактируемый текст в composer.
- Если доступна загрузка локального пакета, она начинается только после отдельного действия и не включает микрофон.
- Без локального распознавания пользователь может печатать; browser-managed fallback не начинает обработку без отдельного информированного согласия.
- Ни один transcript не отправляется до действия пользователя; приложение не загружает и не сохраняет аудио, а возможная обработка браузером внешним сервисом отдельно раскрыта и никогда не запускается автоматически.
- Все состояния доступны клавиатурой и screen reader; ошибки не приводят к зависшей записи или белому экрану.

## M19. Единый контракт поддерживаемых форматов

**Статус:** выполнен 3 октября 2026 года. Capability-матрица и результаты проверок приведены в [`SUPPORTED_FORMATS.md`](SUPPORTED_FORMATS.md) и [`TESTING_REPORT.md`](../TESTING_REPORT.md).

### Цель

Предотвратить рассинхронизацию между форматом, показанным на стартовом экране, HTML `accept`, backend allowlist/MIME, парсером, viewer и тестовой матрицей. Сохранить текущие 13 заявленных расширений; не добавлять новые без полного пути обработки.

### Основные задачи

1. Составить проверяемую capability-матрицу: расширение, MIME, сигнатура/структурная проверка, native parser, MarkItDown/fallback, renderer, ограничения и текущие fixtures.

Устранить или связать повторные списки в `frontend/src/App.tsx`, `backend/app/services/parsing.py`, `backend/app/services/document_security.py`, `frontend/src/components/OriginalDocumentViewer.tsx` и `frontend/e2e/documents.spec.mjs`. Выбрать минимальную архитектуру в рамках существующих Docker build contexts; не вводить генератор/новый API без доказанной необходимости.
3. Добавить contract-тест, который падает при расхождении разрешённого backend-набора, MIME/signature rules, frontend `accept`, renderer mapping и E2E fixture matrix.
4. Для каждого рекламируемого типа поддерживать synthetic positive fixture полного потока и отрицательные fixtures, где формат должен отклоняться до сохранения.
5. Уточнить интерфейсный список: HTML/HTM как одно семейство; не отображать `.xlsm`, `.xlsb`, изображения и другие не включённые форматы как поддерживаемые.

- Используются существующие fixture generator, Playwright и isolated Compose из `scripts/test-e2e.ps1`.

- Frontend contract для отображаемого списка и `accept`.
- E2E upload → ready/fallback → original viewer → citation → Markdown download для каждого из 13 расширений.
- Security audit для MIME mismatch, ZIP/XML traversal, повреждённых Office-файлов, активного HTML и лимитов.
- Отдельный bounded performance run для больших таблиц; подтвердить пагинацию/виртуализацию и отсутствие whole-page overflow.

### Критерии готовности

- CI тестом подтверждает полное равенство заявленных, разрешённых и отображаемых расширений.
- Каждое из 13 расширений имеет хотя бы один сквозной успешный fixture и проверяемый renderer.
- Ни один незаявленный тип не принимается молча; ошибка соответствует причине.
- Безопасность, fallback, пагинация и исходные файлы сохраняют текущее поведение.
- Размеры и стресс-пределы документированы; тестовый профиль остаётся детерминированным.

## M20. Ленивая загрузка PDF.js и производительность старта

**Статус:** выполнен 4 октября 2026 года. Фактические проверки приведены в [`TESTING_REPORT.md`](../TESTING_REPORT.md).

### Цель

Уменьшить загрузку начального экрана, не открывая PDF и не меняя точность его отображения, OCR-цитат и переходов к источникам.

### Основные задачи

1. Зафиксировать baseline build: во время аудита Vite выдал основной JS chunk около 1,224 KB (364 KB gzip) и отдельный PDF worker около 1,376 KB. Снять network/transfer baseline на `/` без выбранного PDF.
2. Разделить `OriginalDocumentViewer` и PDF renderer так, чтобы `pdfjs-dist` загружался только при открытии PDF. Применить существующие React/Vite механизмы dynamic import/lazy boundary; не добавлять библиотеку ради code splitting.
3. Добавить согласованные loading/error состояния для PDF chunk и worker: повтор загрузки, сохранение выбранной citation и доступная ошибка при сетевом/загрузочном сбое.
4. Убедиться, что `pdf.worker` остаётся отдельным asset и загружается только когда PDF renderer действительно запущен.
5. Проверить все другие renderers, чтобы разделение компонента не поменяло lazy state, выбранный источник, OCR box overlay, scaling, fit-to-width, page navigation и расположение панелей.
6. Добавить build/network budget test или reproducible script для размера первоначально загружаемого JS и запроса PDF.js только при открытии PDF.

### Зависимости

- Текущая конфигурация Vite в `frontend/vite.config.ts`, `frontend/src/App.tsx` и `frontend/src/components/OriginalDocumentViewer.tsx`.
- Baseline из аудита; текущий PDF viewer и citations служат regression benchmark.

### Проверки

- Frontend unit/build; проверка manifest, что стартовый route chunk не включает PDF.js.
- Playwright network assertion: открытие стартового экрана не запрашивает PDF.js; при открытии PDF viewer chunk загружается по требованию, а PDF worker создаёт ровно один Worker instance. Браузер может выполнить дополнительный кэшированный fetch того же worker asset.
- E2E PDF: native text, mixed OCR, rotated/CropBox pages, citations и word boxes, retry/error path.
- E2E non-PDF: DOCX, table, PPTX/EPUB, text остаются загружаемыми и не теряют viewer.
- 1440×900, 1024×768 и 390×844; измерить первый paint/start transfer и время до первой отрисовки PDF.

### Критерии готовности

- Без открытия PDF браузер не загружает PDF.js chunk или worker.
- Gzip-объём стартового JS сокращён минимум на 20% относительно зафиксированного baseline 364 KB либо отчёт показывает, почему более строгий budget недостижим и какой фактически подтверждённый порог принят.
- Открытый PDF сохраняет текущий вид, цитаты, OCR-подсветку, переходы и повтор рендера.
- Ошибка загрузки динамического chunk не ломает остальную страницу и доступна для повтора.

**Итог приёмки:** стартовый JS составляет 266,659 байт gzip против baseline 363,239 байт (снижение 26.6%). На чистом экране и при загрузке не-PDF PDF viewer и worker не запрашиваются. При открытии PDF viewer chunk и отдельный worker загружаются по требованию; повторный запуск после отказа chunk/worker сохраняет citation. 31 Chromium E2E прошёл для всех заявленных форматов, связанных viewer/citation flow, кодировок, пагинации и OCR; focused M20-набор затем повторно прошёл 5/5, включая DOCX без PDF-запросов и сохранение citation при отказе worker. Browser-приёмка M20 прошла на 1440×900, 1024×768 и 390×844. Production bundle по-прежнему вызывает информационное предупреждение Vite о chunk больше 500 kB без gzip; бюджет стартовой gzip-загрузки выполнен.

## M21. Сравнение явно выбранных документов

### Цель

Позволить пользователю вести один отдельный разговор о нескольких выбранных документах и сравнивать их с citation на каждый источник, не открывая модели доступ ко всей библиотеке.

### Основные задачи

1. Спроектировать новый тип разговора и additive DB/API migration. Сегодня `Chat.scope` различает `document` и `application`, а document-chat связывает чат с одним `document_id` ([`backend/app/models.py`](../backend/app/models.py), [`backend/app/services/retrieval.py`](../backend/app/services/retrieval.py)). Сохранить старые связи document chat и отдельный app-help chat без переезда истории.
2. Добавить явный список документов разговора с устойчивым порядком и записью версий источников. Не использовать выбранный активный документ как неявное разрешение на чтение других документов.
3. В библиотеке дать выбрать 2–5 готовых документов и ясно показать их в заголовке/панели контекста. Не разрешать добавить pending/failed файлы; пользователь может изменить набор, удалить источник или начать отдельный чат.
4. Расширить API validation: пользователь может ссылаться только на существующие `ready` документы из локальной библиотеки; все document IDs проверяются до retrieval. Ни frontend, ни модель не могут предоставить произвольный путь к файлу или индекс.
5. Добавить retrieval только по выбранному набору: распределять ограничение источников между файлами, сохранять version/source identity и не допускать вытеснения всех результатов одного документа другим.
6. Обновить системные инструкции и контракт citation, чтобы сравнения явно называли документ и приводили отдельные проверяемые источники. При отсутствии доказательств в одном документе так и сообщать, не переносить факт из другого.
7. Расширить frontend state, library/chat selection, stream events и citation navigation. При открытии citation сначала выбрать связанный документ, затем открыть оригинал и locator; если источник удалён/версия недоступна, показать recoverable сообщение.
8. Обеспечить удаление/переименование документа, новое сообщение, retry/stop, смену состава набора и перезапуск приложения без смешивания контекста. Обозначать в чате точный текущий набор документов.
9. Проверить стоимость/латентность, ограничить размер retrieval и число документов. Предел 5 документов — MVP-ограничение для явного scope; изменить его можно только по нагрузочным результатам.

### Зависимости

- M17 определил XLSX источники и формулы; M19 закрепил общий форматный/цитатный контракт.
- Миграция должна пройти приёмку на копии предыдущей схемы и сохранить APP-M01–APP-M03, M12 контекст и M15 обслуживание данных.

### Проверки

- Migration: старые document chats, messages, citations, application chats и bookmarks остаются доступны после upgrade.
- Backend: выбор только ready документов; лимит и уникальность; retrieval исключает unselected документы; независимая квота evidence; удаление/отмена без orphan associations.
- AI contract: отдельные citations document A и B; отсутствие переноса факта между файлами; неизвестный ответ; prompt injection в одном документе не меняет правила обработки другого.
- Frontend E2E: выбрать 2 документа, получить ответ, проверить citations из обоих, перейти по ним к правильным исходникам, перезагрузить страницу, поменять набор и проверить отсутствие citation к чужому/невыбранному документу.
- Privacy regression: app-help chat не читает документы; обычный single-document chat продолжает использовать только один активный документ.
- Проверить upload/retry/delete/version change, длинные имена файлов, повторяющиеся имена и mobile layout.

### Критерии готовности

- Новый multi-document chat после перезапуска сохраняет только явно выбранный набор из 2–5 документов.
- Для каждого citation известны документ, его версия и исходный locator; переход открывает правильный файл и область.
- Попытка добавить неподдерживаемый, неготовый или невыбранный документ отклоняется backend.
- Старые document и application чаты проходят миграцию и их regression-тесты без изменения содержания.
- Ни один тест не обнаруживает retrieval или передачу модели данных документа вне текущего явного набора.

### Итог выполнения

M21 завершён 4 октября 2026 года. В библиотеке можно создать отдельный чат с 2–5 явно выбранными готовыми документами. Связи сохраняют порядок и версию источников; retrieval и payload модели ограничены выбранным набором, а backend проверяет принадлежность каждой цитаты документу. Обновление набора открывает новый `context_epoch`, сохраняя старую историю и citation snapshots; удалённый источник показывает восстанавливаемое состояние, не ломая чат.

Приёмка: полный набор из 107 Chromium E2E прошёл, затем дополнительный comparison E2E прошёл 1/1 для одинаковых длинных имён и мобильного picker; шесть основных viewport проверены. Backend — 445 unit и 11 API integration; frontend — 37 unit/contract; production build и gzip budget прошли; migration downgrade/upgrade сохранил старые данные, а downgrade с comparison chat был отказан; security audit, 13 queue checks, 9 queue acceptance, maintenance и backup/restore прошли. Детали и точные измерения приведены в [`TESTING_REPORT.md`](../TESTING_REPORT.md).
